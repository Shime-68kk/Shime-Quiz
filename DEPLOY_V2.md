# ShimeChamhoc v2 Staging / Beta Deployment Guide

Release candidate: **v2.0.0-rc1**

ShimeChamhoc v2 is a React/Vite static web app. Core learning features run locally in the browser: library import, Study Room, history, analytics, spaced repetition, mastery, recommendations, goals, plans, and backup/restore. No app-owned backend is required for the v2 static deployment.

## 1. Build artifact

Install dependencies and build:

```bash
npm install
npm run build
```

Deploy the generated directory:

```text
dist/
```

Local production preview:

```bash
npm run preview
```

Open:

```text
http://127.0.0.1:4173
```

## 2. Static deployment audit

A valid staging deployment must serve:

- `index.html`
- Vite-generated `assets/*`
- `manifest.webmanifest` if PWA metadata is used
- `icons/*`
- `sw.js` if your deployment keeps service-worker compatibility for older clients

The v2 app entry is generated by Vite from `src/main.jsx`. It should not require direct access to source files in production.

## 3. Base path support

### Root deployment

For root domains such as:

```text
https://example.com/
```

use the default config:

```js
base: './'
```

### Subpath deployment

For subpaths such as:

```text
https://example.com/shimechamhoc/
https://username.github.io/shimechamhoc/
```

use a matching Vite base at build time. Example:

```js
// vite.config.js
export default defineConfig({
  plugins: [react()],
  base: '/shimechamhoc/'
});
```

The React router uses `import.meta.env.BASE_URL` as its basename, so the router and asset paths stay aligned when the Vite base is configured.

Do not use absolute localhost paths in production.

## 4. SPA routing fallback

The host must return `index.html` for client routes such as:

- `/dashboard`
- `/library`
- `/study-room`

Without this fallback, direct route refreshes can return 404 even though in-app navigation works.

## 5. Netlify

Recommended settings:

```text
Build command: npm run build
Publish directory: dist
```

This repository includes `netlify.toml` with:

- build output set to `dist`
- SPA fallback to `/index.html`
- safe cache headers for Vite assets, `index.html`, `manifest.webmanifest`, and `sw.js`

Deploy steps:

1. Connect repository or drag/drop `dist/`.
2. Use the settings above.
3. Open `/dashboard`, `/library`, and `/study-room` directly.
4. Run the staging smoke checklist below.

## 6. Vercel

Recommended settings:

```text
Framework preset: Vite
Build command: npm run build
Output directory: dist
```

This repository includes `vercel.json` with:

- SPA fallback to `/index.html`
- immutable cache for hashed assets
- no-cache headers for `index.html` and `sw.js`

Deploy steps:

1. Import the project into Vercel.
2. Confirm the Vite preset and `dist` output.
3. Deploy preview.
4. Test direct route refreshes.

## 7. Cloudflare Pages

Recommended settings:

```text
Framework preset: Vite
Build command: npm run build
Build output directory: dist
```

This repository includes:

- `_headers` for safe static cache headers
- `_redirects` for SPA fallback

Deploy steps:

1. Create a Pages project.
2. Use the settings above.
3. Confirm `_redirects` is present in the deployed output. If your pipeline does not copy root static config files automatically, copy `_headers` and `_redirects` into the published artifact.
4. Test direct route refreshes.

## 8. GitHub Pages

GitHub Pages commonly serves apps under a repository subpath. For a repository named `shimechamhoc`, configure:

```js
base: '/shimechamhoc/'
```

Then build and deploy `dist/`.

Important notes:

- GitHub Pages does not support server-side rewrite rules like Netlify/Vercel.
- Direct refresh of `/dashboard` can 404 unless you use a Pages-compatible fallback strategy, such as a copied `404.html` fallback or hash routing in a future phase.
- For this RC, prefer testing GitHub Pages from the app root URL and navigating inside the app, or add the `404.html` fallback in the deployment pipeline.

## 9. PWA / service worker notes

The v2 React app is static/local-first and PWA-friendly. A deploy-safe `sw.js` is included in the public deployment artifact mainly for service-worker update compatibility on origins that previously had a registered worker. The v2 React entry does not add a new service-worker registration in this phase. If a staging host serves or already has a registered service worker:

- serve `sw.js` from the same path scope as `index.html`
- do not cache `sw.js` with long immutable headers
- keep the service worker cache version aligned with the release, currently `shimechamhoc-v2.0.0-rc1`
- verify `sw.js` does not precache source-only paths such as `/src/*` in production
- deploy the full build together to avoid mixed old/new assets
- ask beta testers to hard reload or clear site data if stale behavior appears

Current deployment configs set `sw.js` to `no-cache` when served.

## 10. Security/dependency note

The v2 app is local-first. It stores data in browser storage and can export local JSON backups. Full backups may contain question text, correct answers, explanations, and study history. Redacted/progress-only exports reduce sharing risk but are not encryption.

No backend is required for core v2 learning flows. Offline/local scoring requires answers to exist on the client, so true answer-key protection requires a future server-side scoring architecture.

If an optional legacy or future AI explanation button is present, it may call an external endpoint such as:

```text
https://quizct11.onrender.com/api/explain
```

That feature is optional and can be unavailable without breaking v2 local learning flows.

## 11. Rollback instructions

1. Redeploy the previous known-good static artifact.
2. Ask testers to hard reload once.
3. If stale local behavior remains, ask testers to clear site data for the staging origin.
4. If a service worker is active, unregister it from browser DevTools and reload.
5. Re-run the staging smoke checklist.

## 12. Staging smoke checklist

Use a clean browser profile or clear site data before the first pass.

1. Fresh-load the staging root URL.
2. Direct-refresh `/dashboard`.
3. Direct-refresh `/library`.
4. Direct-refresh `/study-room`.
5. Import a valid JSON library file.
6. Import a valid CSV file.
7. Reload and confirm local library persistence.
8. Open Study Room and complete a session.
9. Confirm result summary appears.
10. Confirm history detail appears on Dashboard.
11. Confirm analytics/mastery/review schedule update.
12. Start **Ôn tập hôm nay** when due items exist.
13. Start **Luyện tập thông minh**.
14. Export a full backup and restore it.
15. Export redacted and progress-only backups.
16. Confirm redacted/progress-only restore is blocked with Vietnamese explanation.
17. Check mobile width around 320–390px.
18. Check keyboard navigation for sidebar/bottom nav, import, study actions, and backup buttons.
19. If PWA/service worker is active, reload twice and confirm no stale-cache loop.
20. Confirm no unexpected red console errors.

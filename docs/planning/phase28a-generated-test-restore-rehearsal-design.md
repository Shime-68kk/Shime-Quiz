## Generated/test restore rehearsal problem statement

The restore flow in Shime Quiz is backed by backup files created from localStorage. A key evidence gap is whether the restore flow behaves correctly when given a well-formed backup fixture — without touching real learner data or overwriting production state.

A generated/test restore rehearsal is a test-harness-only dry run of restore-related planning logic against synthetically generated backup fixtures. It:

- Uses only synthetic backup data generated by the test harness (never scanned or derived from real learner data).
- Does not write to localStorage, IndexedDB, or any production storage.
- Does not execute the production restore path.
- Does not change backup file format.
- Does not change restore overwrite behavior.
- Does not create browser/manual evidence.

The goal is to model what a safe test-only restore rehearsal planner would look like, before any runtime implementation.

## Generated/test data rule

All inputs to any future restore rehearsal planner must be synthetically generated by the test harness.

- No real learner data may be used.
- No localStorage snapshot of a real user session may be used.
- No platform backup file from a real device may be used.
- No IndexedDB snapshot from a real user session may be used.

Generated/test data includes:
- Synthetically constructed JSON objects matching the expected backup structure.
- Hard-coded fixture constants defined in test files.
- Programmatically generated records with synthetic IDs, timestamps, and scores.

## No-real-learner-data boundary

Phase 28A and all future phases derived from Phase 28A must not:

- Scan or read real learner content from any storage medium.
- Use a real user's localStorage export as input.
- Derive fixture data from real user behavior.
- Include real learner data in test fixtures.

This boundary applies even if real data is "anonymized" or "truncated."

## No-write and no-overwrite boundary

Phase 28A and all phases derived from Phase 28A (until a separate production write gate is approved) must not:

- Write to localStorage.
- Write to IndexedDB.
- Write to any production storage driver.
- Call `localStorage.setItem`, `localStorage.removeItem`, or `localStorage.clear`.
- Call any IndexedDB write transaction.
- Overwrite existing backup data.
- Overwrite existing learner progress.
- Execute the production restore import path against real storage.

The restore rehearsal planner (to be designed in Phase 28B) must be a pure-function planning model. It may only return a plan or summary object — it must not execute any writes.
